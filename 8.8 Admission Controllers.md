# Admission Controllers

Los Admission Controllers en Kubernetes son como un filtro inteligente que se ejecuta antes de que un recurso se guarde en etcd (es decir, antes de que realmente exista en el cluster).

Cuando haces un request al API Server (por ejemplo: crear un Pod), Kubernetes no lo acepta directamente.

1. Autenticación → ¿Quién eres?
2. Autorización → ¿Tienes permiso?
3. Admission Controllers → ¿Está permitido y/o hay que modificarlo?

Los Admission Controllers pueden:

1. Validar (Validating)

Deciden si el request es válido o no.

Ejemplo:

- Rechazar un pod sin resources.limits
- Bloquear imágenes desde Docker Hub

2. Mutar (Mutating)

Modifican el objeto antes de guardarlo.

Ejemplo:

- Añadir labels automáticamente
- Inyectar sidecars (como Istio)
- Establecer valores por defecto

## Tipos principales

**Mutating Admission Controllers**

- Se ejecutan primero
- Pueden modificar el objeto

Ejemplo:

- MutatingAdmissionWebhook

**Validating Admission Controllers**

- Se ejecutan después
- Solo validan (no modifican)

Ejemplo:

- ValidatingAdmissionWebhook

## Admission Controllers built-in (nativos)

Kubernetes ya trae varios:

Seguridad

- PodSecurity → reemplazo moderno de PodSecurityPolicy
- NodeRestriction

Defaults

- DefaultStorageClass
- DefaultTolerationSeconds

Buenas prácticas

- NamespaceLifecycle
- LimitRanger
- ResourceQuota

**Configuración en el API Server**

Se usan estos dos flags:

```sh
--enable-admission-plugins=
--disable-admission-plugins=
```

**Ejemplo práctico**

Supongamos que quieres activar:

- NamespaceLifecycle
- LimitRanger
- ResourceQuota

```sh
--enable-admission-plugins=NamespaceLifecycle,LimitRanger,ResourceQuota
```
