# Admission Controllers

Los Admission Controllers en Kubernetes son como un filtro inteligente que se ejecuta antes de que un recurso se guarde en etcd (es decir, antes de que realmente exista en el cluster).

Cuando haces un request al API Server (por ejemplo: crear un Pod), Kubernetes no lo acepta directamente.

1. Autenticación → ¿Quién eres?
2. Autorización → ¿Tienes permiso?
3. Admission Controllers → ¿Está permitido y/o hay que modificarlo?

Los Admission Controllers pueden:

1. Validar (Validating)

Deciden si el request es válido o no.

Ejemplo:

- Rechazar un pod sin resources.limits
- Bloquear imágenes desde Docker Hub

2. Mutar (Mutating)

Modifican el objeto antes de guardarlo.

Ejemplo:

- Añadir labels automáticamente
- Inyectar sidecars (como Istio)
- Establecer valores por defecto

## Tipos principales

**Mutating Admission Controllers**

- Se ejecutan primero
- Pueden modificar el objeto

Ejemplo:

- MutatingAdmissionWebhook

**Validating Admission Controllers**

- Se ejecutan después
- Solo validan (no modifican)

Ejemplo:

- ValidatingAdmissionWebhook

## Admission Controllers built-in (nativos)

Kubernetes ya trae varios:

Seguridad

- PodSecurity (reemplazo moderno de PodSecurityPolicy): Aplica políticas de seguridad a los Pods a nivel de namespace.
- NodeRestriction: Limita lo que puede hacer un kubelet (nodo) en el API Server.

Defaults

- DefaultStorageClass: Asigna automáticamente un StorageClass si no especificas uno.
- DefaultTolerationSeconds: Agrega tolerations por defecto a los Pods.

Buenas prácticas

- NamespaceLifecycle: Controla el ciclo de vida de los namespaces.
- LimitRanger: Aplica límites y valores por defecto a recursos.
- ResourceQuota: Limita el uso total de recursos por namespace.

**Configuración en el API Server**

Se usan estos dos flags:

```sh
--enable-admission-plugins=
--disable-admission-plugins=
```

**Ejemplo práctico**

Supongamos que quieres activar:

- NamespaceLifecycle
- LimitRanger
- ResourceQuota

```sh
--enable-admission-plugins=NamespaceLifecycle,LimitRanger,ResourceQuota
```

## PodSecurity

PodSecurity funciona a nivel de namespace usando labels que definen el nivel de seguridad:

- privileged (menos restrictivo)
- baseline
- restricted (más seguro)

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: seguro
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
```

Esto significa: “Todos los pods en este namespace deben cumplir reglas estrictas de seguridad”

**Ejemplo de Pod que será RECHAZADO**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-inseguro
  namespace: seguro
spec:
  containers:
  - name: app
    image: nginx
    securityContext:
      privileged: true
```

Resultado:

- Será bloqueado por PodSecurity
- Porque privileged: true no está permitido en restricted


**Ejemplo de Pod válido (cumple restricted)**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-seguro
  namespace: seguro
spec:
  securityContext:
    runAsNonRoot: true
  containers:
  - name: app
    image: nginx
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
```

Este pod:

- No usa root
- No es privilegiado
- No permite escalamiento
- Tiene filesystem de solo lectura

Cumple con el nivel restricted

### Modos de PodSecurity (muy importante)

Puedes usar 3 modos:

1. enforce (bloquea)

```sh
pod-security.kubernetes.io/enforce: restricted
```

2. audit (solo registra)

```sh
pod-security.kubernetes.io/audit: restricted
```

3. warn (advierte)

```sh
pod-security.kubernetes.io/warn: restricted
```

En producción se usa mucho:

- warn primero
- luego enforce

**Resumen**

- PodSecurity se configura con labels en el namespace
- No necesitas webhooks ni herramientas externas
- Bloquea pods inseguros automáticamente
- Es el reemplazo de PodSecurityPolicy

## LimitRange

LimitRanger trabaja a nivel de namespace y sirve para:

- Definir valores por defecto (requests/limits)
- Restringir mínimos y máximos
- Rechazar pods que no cumplan las reglas

1. Crear un Namespace

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: limites-demo
```

2. Crear el LimitRange

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: limites-container
  namespace: limites-demo
spec:
  limits:
  - type: Container
    default:
      cpu: "500m"
      memory: "256Mi"
    defaultRequest:
      cpu: "200m"
      memory: "128Mi"
    max:
      cpu: "1"
      memory: "512Mi"
    min:
      cpu: "100m"
      memory: "64Mi"
```

Para cada contenedor en ese namespace:

- Si NO defines recursos Kubernetes asigna automáticamente:

```yaml
requests:
  cpu: 200m
  memory: 128Mi
limits:
  cpu: 500m
  memory: 256Mi
```

- Si te pasas del máximo Será rechazad

```yaml
resources:
  limits:
    cpu: "2"
```

- Si estás por debajo del mínimo también será rechazado

```yaml
resources:
  requests:
    cpu: "50m"
```

Ejemplo de Pod válido

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-ok
  namespace: limites-demo
spec:
  containers:
  - name: app
    image: nginx
    resources:
      requests:
        cpu: "300m"
        memory: "200Mi"
      limits:
        cpu: "800m"
        memory: "400Mi"
```

## ResourceQuota

ResourceQuota se usa para limitar el consumo total de recursos dentro de un namespace. Es clave cuando tienes varios equipos/apps compartiendo el cluster.

**Cómo usarlo (paso a paso)**

1. Crear un Namespace

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: equipo-a
```

2. Definir el ResourceQuota

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: quota-equipo-a
  namespace: equipo-a
spec:
  hard:
    requests.cpu: "2"
    requests.memory: 2Gi
    limits.cpu: "4"
    limits.memory: 4Gi
    pods: "5"
```

**¿Qué significa esto?**


Dentro del namespace equipo-a:

- Máximo 2 CPUs en requests
- Máximo 4 CPUs en limits
- Máximo 2Gi RAM (requests)
- Máximo 4Gi RAM (limits)
- Máximo 5 pods

** Ejemplo rechazado**

Si ya tienes 5 pods y creas otro tendras el error:

```sh
exceeded quota: quota-equipo-a, requested: pods=1, used: pods=5, limited: pods=5
```

**Qué puedes limitar**

- CPU
- Memoria
- Pods
- Services
- ConfigMaps
- Secrets
- PersistentVolumeClaims
- Storage
- LoadBalancers

- Para ver el resourceQuota

```sh
kubectl get resourcequota -n equipo-a
```
