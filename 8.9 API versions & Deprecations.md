# API versions

El versionamiento de APIs en Kubernetes es lo que permite que el sistema evolucione sin romper los manifests ni las aplicaciones. Es una de las claves para mantener compatibilidad hacia atrás mientras se introducen mejoras.

Cada recurso en Kubernetes tiene un campo:

```sh
apiVersion: <grupo>/<versión>
```

Ejemplo:

```sh
apiVersion: apps/v1
kind: Deployment
```

Esa versión (v1) indica qué “madurez” y estabilidad tiene la API.

## Tipos de versiones en Kubernetes

Kubernetes usa 3 niveles principales:

### Alpha (v1alpha1, v2alpha1…)

- Muy experimental
- Puede cambiar o desaparecer sin aviso
- Deshabilitada por defecto en muchos clusters

Ejemplo:

```sh
apiVersion: networking.k8s.io/v1alpha1
```
### Beta (v1beta1, v2beta1…)

- Más estable, pero aún puede cambiar
- Bastante usada en el pasado
- Puede ser deprecada

Ejemplo clásico:

```sh
apiVersion: apps/v1beta1 
```

###  Stable / GA (v1, v2…)

- Estable (General Availability)
- Compatible hacia atrás
- Recomendado para producción

```sh
apiVersion: apps/v1
```

**¿Cómo evoluciona una API**

alpha → beta → stable (GA)

# Deprecations

Las siguientes reglas rigen la obsolescencia de elementos de la API. Esto incluye:

- Recursos REST (también conocidos como objetos de la API)
- Campos de los recursos REST
- Anotaciones en los recursos REST, incluidas las anotaciones "beta", pero no las "alpha".
- Valores enumerados o constantes
- Estructuras de configuración de componentes

Estas reglas se aplican entre versiones oficiales, no entre confirmaciones arbitrarias en las ramas master o release.

### Rule #1: Los elementos de la API solo se pueden eliminar incrementando la versión del grupo de la API.

Una vez que un elemento de API se ha agregado a un grupo de API en una versión determinada, no se puede eliminar de esa versión ni modificar significativamente su comportamiento, independientemente de la versión.

### Rule #2: Los objetos de la API deben poder intercambiar información entre las distintas versiones de la API dentro de una misma versión, sin pérdida de información, con la excepción de los recursos REST completos que no existen en algunas versiones.


Por ejemplo, un objeto se puede escribir como v1, leer como v2 y convertir a v1, y el recurso v1 resultante será idéntico al original. La representación en v2 podría ser diferente de la de v1, pero el sistema sabe cómo convertirlas en ambas direcciones. Además, cualquier campo nuevo añadido en v2 debe poder transferirse a v1 y viceversa, lo que significa que v1 podría tener que añadir un campo equivalente o representarlo como una anotación.

### Rule #3: Una versión de API en una determinada rama no puede ser descontinuada en favor de una versión de API menos estable.

- Las versiones de API de disponibilidad general (GA) pueden reemplazar las versiones beta y alfa.
- Las versiones beta de la API pueden reemplazar versiones beta y alfa anteriores, pero no necesariamente las versiones de API de disponibilidad general.
- Las versiones alfa de la API pueden reemplazar versiones alfa anteriores, pero no necesariamente las versiones de API de disponibilidad general ni beta.

### Rule #4a: La vida útil de la API está determinada por el nivel de estabilidad de la API.

- Las versiones de API GA pueden marcarse como obsoletas, pero no deben eliminarse dentro de una versión principal de Kubernetes. 
- Las versiones beta de la API se consideran obsoletas transcurridos 9 meses o 3 versiones menores desde su introducción (lo que ocurra más tarde), y dejan de recibir soporte transcurridos 9 meses o 3 versiones menores desde su obsolescencia (lo que ocurra más tarde). 
- Las versiones alfa de la API pueden eliminarse en cualquier versión sin previo aviso de obsolescencia.

Esto garantiza que la compatibilidad con la API beta cubra el máximo desfase de versiones admitidas de 2 versiones, y que las API no se estanquen en versiones beta inestables, acumulando un uso en producción que se verá interrumpido cuando finalice la compatibilidad con la API beta.

**Nota**

Actualmente no existen planes para una revisión importante de Kubernetes que elimine las API de disponibilidad general (GA).
