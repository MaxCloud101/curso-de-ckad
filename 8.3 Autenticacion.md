# Autenticación

La autenticación en Kubernetes es el primer paso de seguridad cuando alguien (o algo) intenta hablar con el API Server.

En Kubernetes hay dos tipos de identidades:

<div align="center">
  
| Tipo           | Para quién          |
| -------------- | ------------------- |
| User           | Humanos             |
| ServiceAccount | Pods / aplicaciones |

</div>

El flujo es así:

1. Cliente hace request al API Server (kubectl, Pod, CI/CD, etc.)
2. El API Server intenta autenticar
3. Si pasa → se asigna una identidad (user / service account)
4. Luego entra autorización (RBAC)

**Flujo Simplificado** -> Cliente → API Server → Autenticación → Autorización → Respuesta

## Tipos de autenticación en Kubernetes

Kubernetes soporta varios métodos. Aquí están los principales

### 1. Certificados (X.509 Client Certificates)

Muy común en admins (kubectl)

- Usas un certificado firmado por la CA del cluster
- Kubernetes extrae el usuario del certificado

```sh
kubectl --client-certificate=cert.pem --client-key=key.pem
```

- Seguro
- Difícil de gestionar a gran escala

### 2. Bearer Tokens (Service Accounts)

Usado por Pods

- Token JWT montado automáticamente
- Se envía en el header:

```sh
Authorization: Bearer <token>
```

- Automático
- Ideal para workloads internos

### 3. OIDC (OpenID Connect)

Integración con identity providers

Ejemplos:

- Google
- Microsoft Azure
- Okta

Casos de uso:
- SSO
- Ideal para empresas
- Escalable

### 4. Webhook Token Authentication

Kubernetes delega autenticación a un servicio externo

Flujo:

- API Server recibe token
- Llama a un webhook externo
- El webhook responde si es válido o no

Ideal en casos
- Flexible
- Integrable con sistemas propios

**¿Cómo se configura?**

Se configura en el API Server con un archivo tipo Config:

webhook.yaml
```sh
apiVersion: v1
kind: Config
clusters:
- name: webhook-auth
  cluster:
    server: https://mi-webhook-auth.com/validate
```

Y luego se pasa como flag:

```sh
--authentication-token-webhook-config-file=/path/webhook.yaml
```

El API Server envía un JSON como este:

```sh
{
  "apiVersion": "authentication.k8s.io/v1",
  "kind": "TokenReview",
  "spec": {
    "token": "abc123"
  }
}
```

¿Qué debe responder el webhook?

```sh
{
  "apiVersion": "authentication.k8s.io/v1",
  "kind": "TokenReview",
  "status": {
    "authenticated": true,
    "user": {
      "username": "usuario1",
      "uid": "123",
      "groups": ["dev"]
    }
  }
}
```

Una vez validado del token puedes usarlo para hacer request al API server

1. Usando curl

```yaml
TOKEN="abc123"

curl https://<API_SERVER>/api/v1/pods \
  -H "Authorization: Bearer $TOKEN" \
  --insecure
```

2. Usando kubectl

```yaml
apiVersion: v1
kind: Config
users:
- name: usuario-webhook
  user:
    token: abc123
```

### 5. Static Token File (no recomendado)

Tokens definidos en un archivo en el API Server

```sh
<token>,<username>,<uid>,<groups>
```

Ejemplo:

tokens.csv
```sh
abc123,max,1001,dev
xyz789,admin,1002,admins
```

- No escalable
- Poco seguro
- Solo para pruebas

**¿Cómo se configura?**

Se pasa como flag:

```sh
--token-auth-file=/etc/kubernetes/tokens.csv
```

Kubernetes cargará ese archivo al iniciar

Luego puedes hacer request

1. Usando curl

```yaml
TOKEN="abc123"

curl https://<API_SERVER>/api/v1/pods \
  -H "Authorization: Bearer $TOKEN" \
  --insecure
```

2. Usando kubectl

```yaml
apiVersion: v1
kind: Config
users:
- name: static-user
  user:
    token: abc123
```

```sh
kubectl --user=static-user get pods
```

### 6. Anonymous (opcional)

Requests sin autenticación, al kube api server se le pasa el flag:

```sh
--anonymous-auth=true
```

Generalmente deshabilitado o muy restringido
