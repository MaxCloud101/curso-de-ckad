# Autorización

La autorización en Kubernetes (K8s) es el proceso de seguridad que determina qué acciones (verbos como get, create, delete) pueden realizar los usuarios o servicios autenticados sobre recursos específicos (como pods o deployments) dentro del clúster. 

Cuando haces una request al API Server:

Autenticación → Autorización → Admission Controllers

1. Autenticación → quién eres
2. Autorización → qué puedes hacer
3. Admission → reglas adicionales (validaciones/mutaciones)

**¿Qué evalúa la autorización?**

Cada request se evalúa con estos atributos:

- Usuario / ServiceAccount
- Recurso (pods, deployments, etc.)
- Namespace (si aplica)
- Verbo (get, list, create, delete, etc.)
- API Group

Ejemplo mental:

¿El usuario "juan" puede hacer "delete" sobre "pods" en "default"?

## Módulos de autorización (Authorization Modes)

### 1. RBAC (Role-Based Access Control)

RBAC es un método de seguridad en Kubernetes para regular quién (usuarios o procesos) puede acceder a qué recursos (Pods, Deployments, etc.) y qué acciones realizar (crear, listar, eliminar). Utiliza el grupo de API rbac.authorization.k8s.io para gestionar permisos dinámicamente, asegurando que los usuarios solo tengan los privilegios necesarios.

Define permisos usando:

- Roles / RoleBindings
- ClusterRoles / ClusterRoleBindings

Rol que permite leer pods
```
kind: Role
apiVersion: rbac.authorization.k8s.io/v1
metadata:
  namespace: default
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list"]
```

Asignar el rol a un usuario
```
kind: RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
metadata:
  name: read-pods
  namespace: default
subjects:
- kind: User
  name: juan
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**Resultado:**
juan puede leer pods en default, pero no borrarlos

### 2. RBAC (Role-Based Access Control)

La autorización ABAC (Attribute-Based Access Control) en Kubernetes es uno de los mecanismos más antiguos (y hoy en día deprecado en la práctica) para decidir qué acciones puede realizar un usuario sobre el API Server.

ABAC usa un archivo tipo JSON (una política por línea).

abac-policy.json
```json
{"user":"juan","namespace":"prod","resource":"pods","verb":"get"}
{"user":"juan","namespace":"prod","resource":"pods","verb":"list"}
{"group":"backend","namespace":"prod","resource":"deployments","apiGroup":"apps","verb":"create"}
{"user":"admin","apiGroup":"*","resource":"*","verb":"*"}
```
Campos: 
- user: usuario específico
- group: grupo de usuarios
- namespace: namespace donde aplica
- resource: recurso (pods, deployments, services…)
- apiGroup: grupo del API ("" para core)
- verb: acción permitida

**Configura en el API Server**

```sh
--authorization-mode=ABAC
--authorization-policy-file=/ruta/abac-policy.json
```

### 3. Webhook Authorization

La Webhook Authorization en Kubernetes es un mecanismo avanzado donde el API Server delegaa la decisión de autorización a un servicio externo (un webhook).

En vez de decidir internamente (como con RBAC o ABAC), Kubernetes le pregunta a otro sistema

Usuario → API Server → Webhook → API Server → Resultado

**Configuración en el API Server**

Es un archivo tipo kubeconfig:

webhook-config.yaml
```yaml
apiVersion: v1
kind: Config
clusters:
- name: webhook-auth
  cluster:
    server: https://mi-webhook:8443/authz
    certificate-authority: /etc/kubernetes/pki/ca.crt

users:
- name: kube-apiserver
  user:
    client-certificate: /etc/kubernetes/pki/apiserver.crt
    client-key: /etc/kubernetes/pki/apiserver.key

contexts:
- context:
    cluster: webhook-auth
    user: kube-apiserver
  name: webhook-context

current-context: webhook-context
```

Se habilita en el API Server:

```sh
--authorization-mode=Webhook
--authorization-webhook-config-file=/ruta/webhook-config.yaml
```

Kubernetes envía un objeto JSON llamado:

```json
{
  "apiVersion": "authorization.k8s.io/v1",
  "kind": "SubjectAccessReview",
  "spec": {
    "user": "max",
    "group": ["devs"],
    "resourceAttributes": {
      "namespace": "default",
      "verb": "get",
      "resource": "pods"
    }
  }
}
```

Responde algo similar:

```json
{
  "apiVersion": "authorization.k8s.io/v1",
  "kind": "SubjectAccessReview",
  "status": {
    "allowed": true,
    "reason": "User has access"
  }
}
```

### 4. Webhook Authorization

La Node Authorization en Kubernetes es un modo de autorización especializado que controla qué puede hacer cada nodo (kubelet) dentro del cluster. Es una política de mínimo privilegio automática para nodos.

**¿Cómo funciona?**

Cuando un kubelet hace una petición al API Server:

1. El kubelet se autentica (normalmente como system:node:<node-name>)
2. Kubernetes aplica el modo de autorización Node
3. Evalúa:
  - ¿Este nodo está intentando acceder a recursos relacionados con sus Pods?
  - ¿Está intentando acceder a otros nodos o recursos globales?

- Si está dentro de su scope → ✅ permitido
- Si intenta salirse → ❌ denegado

**¿Por qué existe?**

Sin Node Authorization, un kubelet comprometido podría:

- Leer TODOS los Secrets del cluster
- Escalar privilegios
- Comprometer toda la infraestructura

Node Authorization limita ese daño.

**Configuración en el API Server**

```sh
--authorization-mode=Node,RBAC
```

### 5. AlwaysAllow / AlwaysDeny

#### AlwaysAllow

Permite TODO sin validar nada.

**Configuración en el API Server**

```sh
--authorization-mode=AlwaysAllow
```

#### AlwaysDeny

Deniega TODO sin excepción.

**Configuración en el API Server**

```sh
--authorization-mode=AlwaysDeny
```

**¿Para qué sirven realmente?**

AlwaysAllow

- Testing rápido
- Entornos locales
- Debug

AlwaysDeny

- Testing de fallos
- Validar que no hay accesos accidentales
