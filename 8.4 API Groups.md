# API Groups

Los API Groups en Kubernetes son una forma de organizar y versionar la API para evitar conflictos y permitir que el sistema crezca sin romper compatibilidad.

Kubernetes no tiene una sola API plana, sino varias agrupadas así:

```sh
/api/v1                ← Core API Group
/apis/apps/v1          ← API Group "apps"
/apis/batch/v1         ← API Group "batch"
/apis/networking.k8s.io/v1
```

## Tipos de API Groups

### 1. Core API Group (el grupo base)

No tiene nombre explícito
Se accede con: /api/v1

Ejemplos de recursos:

- Pods
- Services
- ConfigMaps
- Secrets

Ejemplo YAML:

```yaml
apiVersion: v1
kind: Pod
```

### 2. Named API Groups (grupos con nombre)

Se accede con /apis/<group>/<version>

Ejemplos comunes:

- apps
- batch
- networking.k8s.io
- rbac.authorization.k8s.io

Ejemplo:

```yaml
apiVersion: apps/v1
kind: Deployment
```

## API Groups y extensibilidad (CRDs)

Cuando creas un Custom Resource Definition (CRD), defines tu propio API Group:

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
spec:
  group: miempresa.com
```

Luego usas:

```yaml
apiVersion: miempresa.com/v1
kind: MiRecurso
```

Esto permite crear APIs como si fueran nativas de Kubernetes

## Relación con apiVersion

| apiVersion             | Grupo             | Versión |
| ---------------------- | ----------------- | ------- |
| `v1`                   | core              | v1      |
| `apps/v1`              | apps              | v1      |
| `batch/v1`             | batch             | v1      |
| `networking.k8s.io/v1` | networking.k8s.io | v1      |



Con API Groups puedes:
- Separar responsabilidades (apps, networking, seguridad)
- Versionar cada grupo de forma independiente
- Extender Kubernetes (CRDs)
